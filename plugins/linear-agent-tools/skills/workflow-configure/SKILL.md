# Configure Linear Workflow

Prepare one exact Linear destination and explicitly selected GitHub repository/base. This skill changes global team/workspace or repository-administration configuration only after preview and explicit approval; it never creates a task Project or mutates Product source.

Read `../../references/manual-workflow.md` and `../../lib/task_graph/issue-contract.md` completely.

## Procedure

1. Resolve the explicit user-level Linear MCP profile. Authenticate interactively when needed; do not add project-local MCP configuration or export its managed token.
2. Read the authenticated viewer, workspace and exact team by immutable IDs. Require active membership, `admin=true`, `guest=false`, and the exact user-approved destination. Names and email are display evidence, never substitutes for IDs.
3. Fully paginate current issue statuses, workspace Project statuses, labels and every team `gitAutomationStates` rule, including target-branch rules. Check GitHub integration by proving that the intended repositories can create official issue-identifier branch/PR links; a manually pasted URL is not proof. For every explicitly selected repository/base, read the authenticated GitHub login, numeric and node identity plus exact repository permission, and form one closed mutation-complete protection snapshot from classic protection, fully paginated effective active branch rules, each exact full ruleset and its bypass actors, and exact required-check definitions. The snapshot includes the pull-request/review gate, strict checks, linear history, signatures, conversation resolution, lock, restrictions, force/delete/admin enforcement, merge queue and every other currently known applicable ruleset type. Unknown rule types, unknown classic fields, incompatible rules and any bypass fail closed; exact write authority is mandatory. Provider failure, malformed or empty output is never absence. Reject missing, disabled, ineffective or bypassed protection.
4. Reconcile exact desired configuration from the shared model. Accept existing standard statuses only when their fixed category matches. The sole rename exception is the exact provider-owned legacy `Human Review` definition: plan an in-place update to `Review` using its existing status ID. In the same identity-preserving migration, update the exact provider-owned legacy `Merging` description so it no longer claims human approval. Treat a changed legacy review definition, duplicate/current-plus-legacy review states, wrong categories and foreign same-name labels as conflicts; never delete or replace the legacy state. Require the complete Git status automation list to be empty because the task provider exclusively owns lifecycle transitions; repository linking remains enabled and independent from status automation.
5. Save the complete freshly MCP-read labels to a transient input and run `scripts/configure.py plan`. On the first read-only plan, `--workspace-id` may be omitted; the authenticated GraphQL read discovers it while still requiring the exact viewer and team IDs. Show the fingerprinted exact destination together with the global delta: identity-preserving issue-status updates, missing issue statuses, Project statuses and labels, exact Git status automation deletion targets, plus any conflict. For each selected GitHub repository/base, separately run `scripts/branch_protection.py plan --merge-method <declared-method>`; show its exact typed snapshot and only `none` or `create-minimal-classic-protection`. Obtain explicit approval for every destination-bound delta and retain each exact plan output only for this transaction.
6. Before any global mutation, run `scripts/configure.py apply` with the exact destination IDs from the approved plan, the fresh unchanged label snapshot and `--approved-plan-input` pointing to the exact displayed plan. The script proves both destination identity and the complete remaining delta against that plan, reads a separate admin-capable credential with no echo, deletes only the exact approved Git status automation rules, updates only the exact approved legacy status IDs, creates only the proven missing statuses and performs its own read-back. Every in-place status update response and final readback must reproduce the preserved legacy ID plus the exact approved name, category, color, description and position; a partial response or replacement identity is failure. It intentionally leaves the still-approved label gap for the official MCP owner. Never pass the credential in argv or environment.
7. Use official MCP operations for the approved missing labels and every operation it supports. For an approved absent GitHub protection delta, run `scripts/branch_protection.py apply --repository <owner/name> --base-branch <base> --merge-method <declared-method> --approved-plan-input <exact-plan>`; it refuses changed or unsafe existing state and creates only classic protection with admin enforcement, force pushes and deletion disabled, no required pull-request reviews, and no required checks. That zero-check configuration is valid only for the two-ref atomic `merge` path. Existing effective protection is never weakened or overwritten, and an incompatible closed snapshot can never produce action `none`. A `squash` or `rebase` protection inspection requires pre-existing no-bypass strict up-to-date protection with at least one required check, but `task-merge` still fails closed before mutation or terminal certification until an equally exact immutable strategy proof exists. Fully reread all configuration through each owner transport, prove empty reconciliation, and recheck GitHub linking. If any step is missing, stop graph publication with one exact bounded human action.

Every preview or handoff response MUST distinguish the fully paginated team issue statuses, workspace Project statuses, labels and Git status automations. State explicitly that the no-echo in-memory GraphQL transaction deletes only exact approved automation rules, preserves the legacy review and Merging status identities while updating their exact recognized definitions, and creates only still-missing approved status definitions before any other global mutation; supported label creation belongs to official Linear MCP operations afterward. Final success requires an exact destination read-back with no remaining delta and an empty Git status automation list.

Also state explicitly that `workflow-configure` never creates or mutates a task Project or issue graph. It only configures the destination and proves GitHub integration; graph publication belongs to `task-graph-create`.

The scripts' required `--labels-input` and apply-only `--approved-plan-input` files are transient complete JSON artifacts produced during the current configuration transaction. They are not credentials or durable configuration files. Delete them after the final read-back.
